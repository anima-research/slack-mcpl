- TCP reconnects keep one Slack forwarding callback and reset peer-owned channel, routing, and backscroll state. Pending work from an old connection cannot alter the next peer's context; subscriptions and rollback checkpoints remain intact (#4).
- Concurrent messages in one conversation share first-interaction preparation and arrive in order, without repeating backscroll. Each optional backscroll or metadata lookup gives up after five seconds and delivery continues without its result. Other conversations remain independent (#4).
- A TCP peer whose handshake fails no longer ends the process: the server closes that connection and waits for the next client. An addressed message dropped because there is no peer, its peer left, or `slack.messaging` was switched off before delivery is logged on stderr. When acknowledgment reactions are configured, the server requests them as addressed messages enter the queue. A dropped or refused message releases its reaction. Send-failure logs name the message and conversation (#4).
- Thread routing and location-header context advance only after the host takes a message. Acceptance records the current peer's delivery context even if its messaging grant changed during the send (#4).
- A first message the host refuses, or that never reaches it, no longer uses up the conversation's first interaction: the next addressed message brings the backscroll, and a mention subscribes a conversation only together with the note saying so. An explicit `subscribe_channel` or `unsubscribe_channel` settles auto-subscription for the rest of the process, even before the first delivery or while the host's answer is pending. That choice holds across reconnects (#4).
