- TCP reconnects keep one Slack forwarding callback and reset peer-owned channel, routing, and backscroll state. Pending work from an old connection cannot alter the next peer's context; subscriptions and rollback checkpoints remain intact (#4).
- Concurrent messages in one conversation share first-interaction preparation and arrive in order, without repeating backscroll. Other conversations remain independent (#4).
- A TCP peer whose handshake fails no longer ends the process: the server closes that connection and waits for the next client. An addressed message dropped because its peer left, or `slack.messaging` was switched off, before delivery is logged on stderr (#4).
- A first message the host refuses, or that never reaches it, no longer uses up the conversation's first interaction: the next one brings the backscroll, and a mention subscribes a conversation only together with the note saying so. A mention still auto-subscribes a conversation at most once per process, so `unsubscribe_channel` holds across reconnects (#4).
