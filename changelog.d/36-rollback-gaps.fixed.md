- A process's first post or upload can now be rolled back, by a host that rolls back to a result's parent. Each `slack.messaging` tool's successful result now names its checkpoint's parent beside the checkpoint (`state: { checkpoint, parent }`, as MCPL §8.2 has it), where it named the checkpoint alone, and the checkpoint tree starts at a root made before anything is sent, where no checkpoint came before the first one. So the first call's result names the root as its parent, and a rollback to the root deletes what that call sent. The root reaches a host only as that parent: a host that keeps nodes only for checkpoints a result named as its own can't roll back to it.
- A post whose answer from Slack names no message (no `ts`, or one that isn't a string) now answers as an unknown outcome, with the check to make before posting again. `send_message`, `reply_message` and `send_dm` used to answer one without a `ts` as a success with an empty `messageId`, and `channels/publish` as delivered with an empty one, an id `reply_message`, `edit_message`, `delete_message` and `add_reaction` refuse. The acknowledgement reaction (`SLACK_ACK_REACTION`) now stays after such a post, as after a post that failed, until Slack confirms a later post in that conversation or the reaction's ten minutes run out.
- Such a post, and one whose call failed in a way that may have posted it, is kept for rollback without an id. A rollback past it sends no delete with an empty `ts`: it counts the post among the messages not deleted, and names it under "May remain" with its conversation, its thread for a reply, and how to find its id. A post that can't have gone out, such as one Slack refused, leaves nothing to roll back, as before.
- A write that fails with a `TypeError`, which the client throws when it can't read Slack's answer, now answers as an unknown outcome, with the check to make, unless a request before the write threw it. It answered with the error's text alone. An acknowledgement reaction whose add failed that way now counts as added, and comes off with the others.
- An upload whose last step fails with an error the client doesn't classify, other than a `TypeError`, such as a 429 without a usable Retry-After, now counts as not shared, as a refused one does, so a rollback no longer notes that its comment may remain.
