- A Slack call that's rate-limited, or that fails on its way to or from Slack, no longer retries for minutes. It says what happened, after waiting out at most 5 seconds of rate limits. Before, the Slack client retried such calls itself, waiting out a rate limit or retrying a network failure or an HTTP error for up to about 30 minutes. Requests are handled one at a time, so every request behind that call waited too. When the client's retries ran past the host's own request timeout, the host answered first and told the agent the outcome was unknown. The client could still post the message afterwards, so an agent that sent it again posted it twice. Now:
  - Each call has 25 seconds from when it reaches this server. A Slack request goes out only if its 10-second timeout fits in what is left of them. A call queued behind slow ones, or whose own earlier requests took most of its time, says at once that the request wasn't sent and that calling again is safe, instead of running past the host's timeout. A write never runs into the deadline, so the deadline never leaves a write's outcome unknown.
  - Each call has 5 seconds in all for waiting out rate limits. When Slack rate-limits one of its requests for no longer than what is left of those seconds, and the request would still fit in the call's time after the wait, the request waits that long and is sent once more, instead of the limit coming back to the agent. Slack refused the first request without acting on it, so nothing is posted twice. A longer limit, one past what is left, or a second limit on the same request answers at once with Slack's Retry-After, for example "Nothing was posted: Slack is rate-limiting this kind of call for the workspace, and asks to wait 30 seconds before trying again." For `list_channels`, `find_user` and `refresh_channels` it adds that a new call starts the listing over from the first page, so in a workspace too large to list within Slack's limit, calling again stops near the same place.
  - A write that fails in transit isn't sent again. Its error says the outcome is unknown and how to check before trying again, so it's never reported as failed when it may have gone through. When the request that failed came before the write itself, such as the conversation check under `SLACK_DISABLE_DMS` or `send_dm`'s `conversations.open`, the error says nothing was written, and to try again shortly. When the connection to Slack couldn't be made at all, or Slack received the request only in part (`request_timeout`), it says nothing was done. A read says to try again.
  - A request fails once Slack has gone 10 seconds without answering, so a read that Slack answers more slowly than that now fails, where it used to wait.
  - A `fetch_attachment` download keeps the same rules: it starts only if 10 seconds fit in what is left of the call's 25, and it fails if the file hasn't finished arriving 10 seconds after it started. Its error says nothing changed and calling again is safe.
  - Work in the background that uses the Web API client no longer waits either, apart from channel registration's listing (below). Socket Mode's own client, which opens the event connection, keeps its library's patience for reconnecting, as before. An acknowledgement reaction that Slack rate-limits isn't added, and one whose removal Slack rate-limits, or that fails in transit, five times a minute apart stays on its message. A message whose users' names Slack doesn't answer for reaches the host up to 10 seconds later for each eight names, with their IDs. A DM that `list_channels` lists while Slack rate-limits or fails its user's lookup is labelled with the user's ID. `refresh_channels` leaves such a DM out if the host doesn't know it yet, and says so and when to call again, since the host keeps the label a conversation is first announced with. A backscroll or a conversation's name that Slack rate-limits or fails to give is left out of the message it was for, as one that took more than 5 seconds already was, and stderr now says so for a failure too. A rollback leaves a message posted when Slack rate-limits its delete for longer than its call can wait or its call's time runs out, and may when the delete fails in transit. Its reason counts the deletes Slack confirmed, stderr names each message it couldn't delete, and a later rollback doesn't try those messages again.
  - Channel registration waits out a page of its conversation listing that Slack answers with an HTTP 429 for as long as its Retry-After asks, then goes on from that page, so a workspace too large to list within Slack's limit still registers. A page that fails in transit, with an HTTP error or by Slack's own failure is asked for again 30 seconds later, and a DM's user lookup, whose name labels the DM in the host, is waited out the same way. Registration gives up on a request, with a log line, once it has been tried ten times in a row: a page it gives up on ends the listing, and a DM whose user's name it gives up on is labelled with the user's ID, as one Slack refuses to look up is, while the listing goes on and looks up its later DMs' users once, without waiting, labelling one whose lookup fails with the ID too. Each of registration's waits is logged on stderr, naming the Slack method, why it waits, the seconds and the try, such as `Slack rate-limited conversations.list (try 1 of 10); registration asks again in 30 s`. A `refresh_channels` during registration, waiting or not, answers at once that registration is still running, and lists once registration has ended. A registration that a revoke or a re-grant superseded holds no refresh back.
  - At startup, `auth.test` still waits out a Slack it can't reach, as before, and each of its tries now gives up after 10 seconds without an answer.
- `add_reaction` with a reaction the bot has already put on the message answers as a success: "Nothing changed: message `<id>` already has this bot's `<emoji>` reaction." It used to be an `already_reacted` error.
- When a user's name can't be looked up because of a rate limit, a failure in transit or a failure on Slack's side, the lookup is tried again with the next message that names the user. Before, the raw user ID stood in for the name for the rest of the process. A user Slack refuses to look up, such as one it doesn't know (`user_not_found`), is still shown by ID without asking again.
- An acknowledgement reaction whose add may have landed is removed at the bot's next post, as an added one is: one Slack answered `already_reacted`, one Slack failed on while handling it (`internal_error`, `fatal_error` or `service_unavailable`), and one that got an HTTP error or failed in transit after it may have reached Slack.
